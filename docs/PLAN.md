# План первого MVP

Обновлено: 20 сентября 2026 года. Первый исполняемый вертикальный срез реализован: web/API, PostgreSQL, зашифрованные сессии, worker и коннекторы ReManga/MangaLib. Остальные пункты ниже остаются планом доведения MVP до закрытой альфы.

## Цель MVP

Пользователь создаёт профиль Manga Hub, подключает аккаунты манга-сайтов и получает одну личную библиотеку с прогрессом чтения по каждому источнику. После первого подключения сервис автоматически обновляет данные примерно раз в час.

MVP не обходит полный каталог площадок. Коннектор получает только:

- произведения, уже добавленные в личную библиотеку подключённого аккаунта;
- статус произведения и папку/список, если источник их предоставляет;
- прочитанные главы либо последний подтверждённый прогресс;
- минимум метаданных, нужный для показа и сопоставления одного произведения между источниками.

Под «синхронизацией между сервисами» в MVP понимается объединение данных в профиле Manga Hub. Сервис ничего не добавляет в библиотеки MangaLib/ReManga и не отмечает там главы прочитанными. Обратная запись рассматривается отдельно после того, как чтение и сопоставление данных окажутся надёжными.

## Принятые решения

- Продукт — сайт с серверным API и отдельным фоновым worker-процессом.
- Код переносим между macOS и Linux. В нём нет Keychain, LaunchAgent и других платформенных зависимостей.
- Локально Node.js-процессы и PostgreSQL запускаются без Docker. На Ubuntu web/API и sync worker запускаются из одного Docker image разными командами, а Chromium живёт в отдельном auth-browser image.
- Основной стек: Next.js, React, TypeScript, PostgreSQL, Drizzle и Playwright.
- Авторизация Manga Hub — Better Auth с PostgreSQL-сессиями и email/password; пароль хешируется Argon2id.
- Очередь и расписание работают поверх PostgreSQL через Graphile Worker. Redis для MVP не нужен.
- Cookies и токены источников сохраняются только в зашифрованном виде. Ключ шифрования не лежит в PostgreSQL, репозитории или Docker image.
- Первый вертикальный срез делается на ReManga, второй — на MangaLib. Готовность MVP требует двух источников, иначе нельзя проверить объединение.
- ReadManga и InkStory подключаются следующими адаптерами после технической проверки личного кабинета и способа входа.

## Пользовательский сценарий

1. Пользователь регистрируется в Manga Hub и входит в профиль.
2. На экране «Подключения» нажимает «Подключить ReManga».
3. Manga Hub создаёт одноразовую браузерную auth-сессию. Пользователь входит непосредственно в открытый сайт источника, включая CAPTCHA или 2FA.
4. После успешного входа worker сохраняет зашифрованное состояние сессии и уничтожает временный браузерный профиль.
5. Сразу запускается первичный импорт личной библиотеки и прогресса.
6. Пользователь так же подключает MangaLib.
7. Manga Hub объединяет уверенные совпадения и показывает спорные пары для ручного подтверждения.
8. Примерно раз в час worker получает изменения из подключённых аккаунтов. Чтение на Android появляется в Manga Hub без дополнительных действий пользователя, если сам источник сохраняет прогресс в аккаунте.
9. Когда сессия источника истекает, подключение получает статус «Нужен повторный вход»; сохранённая библиотека не пропадает.

## Что должно быть доказано до основной разработки

Для каждого источника проводится короткий технический spike на тестовом аккаунте:

1. Открыть главу на Android и убедиться, что точный прогресс виден после входа во втором браузере.
2. Проверить, можно ли перечислить всю личную библиотеку постранично.
3. Установить, отдаёт ли источник явный набор прочитанных глав или только последнюю главу.
4. Найти устойчивый внешний ID произведения и главы.
5. Проверить способ входа, CAPTCHA/2FA, срок жизни сессии и возможность её повторного использования.
6. Измерить безопасную частоту запросов и поведение при `401`, `403`, `429` и `5xx`.

Если точный прогресс хранится только на устройстве читателя, серверная синхронизация этого источника невозможна. Такой адаптер не маскирует отсутствие данных догадкой.

## Этапы реализации

| Этап | Результат | Признак готовности |
| --- | --- | --- |
| 0. Проверка источников | Spike ReManga и MangaLib, зафиксированные возможности адаптеров | На втором устройстве виден серверный прогресс; понятны вход, библиотека, главы и ограничения |
| 1. Каркас сервиса | Next.js, PostgreSQL, Drizzle migrations, Better Auth, Graphile Worker, базовый UI | Пользователь регистрируется, входит и видит пустые «Библиотеку» и «Подключения»; миграции создают БД с нуля |
| 2. Хранилище сессий | Envelope encryption, версии ключей, отдельная роль worker, аудит подключения | В PostgreSQL нет cookies/tokens в открытом виде; worker может сохранить, прочитать и удалить тестовый secret; ротация KEK проверена |
| 3. ReManga end-to-end | Авторизация источника, первичный импорт, read-only progress sync | После подключения видны только тайтлы личной библиотеки и подтверждённый прогресс; повторный импорт не создаёт дублей |
| 4. MangaLib и сопоставление | Второй адаптер, единые произведения, экран спорных совпадений | Один тайтл с двух сайтов показан одной строкой и с двумя независимыми прогрессами; сомнительное совпадение не объединяется молча |
| 5. Автоматическая синхронизация | Почасовые задания, cursors/hashes, backoff, ручной запуск, журнал | Новая глава, прочитанная на телефоне, появляется без повторного входа; перезапуск worker не теряет и не дублирует задания |
| 6. Ubuntu-ready | Dockerfile, Compose, reverse proxy/TLS, browser gateway, backup/restore | Один и тот же commit работает локально без Docker и на чистом Ubuntu через Compose; восстановление БД и ключа проверено |
| 7. Закрытая альфа | ReadManga/InkStory по одному, защита от поломки парсеров | Ошибка одного источника не останавливает остальные и не удаляет ранее сохранённый прогресс |

Этап 0 — обязательный go/no-go. Красивый интерфейс не компенсирует отсутствие серверного прогресса у площадки.

## Алгоритм первичного импорта

```text
проверить зашифрованную сессию
→ получить профиль внешнего аккаунта
→ пройти страницы только личной библиотеки
→ upsert записей source_title и source_library_entry
→ получить прогресс только для найденных записей
→ сохранить исходные метки и доказательства прогресса
→ найти/создать canonical work
→ создать кандидаты неоднозначных совпадений
→ пересчитать представление личной библиотеки
```

Если источник сообщает только «последняя глава 40», это хранится как наблюдение `last_read = 40`. Отдельные главы 1–39 считаются прочитанными только когда семантика источника это гарантирует. Значения `12.5`, `Экстра 4`, `Пролог` и разные разбиения главы сохраняются без округления.

## Алгоритм периодической синхронизации

- Планировщик создаёт одно задание на активное подключение примерно раз в час с небольшим jitter.
- Если источник предоставляет историю или `updated_at`, worker читает только изменения после cursor.
- Если delta-интерфейса нет, worker проходит личную библиотеку до первой неизменившейся страницы по устойчивому hash.
- Раз в неделю выполняется полная сверка личной библиотеки.
- Для одного подключения одновременно выполняется не больше одного задания.
- Все upsert-операции идемпотентны; исходные наблюдения сохраняются отдельно от вычисленного текущего состояния.
- `401` или страница входа переводят подключение в `reauth_required` без бессмысленных повторов.
- `429` учитывает `Retry-After`; временные ошибки получают backoff с jitter.
- CAPTCHA не обходится: подключение получает `needs_attention`.
- Ошибка парсинга не превращается в пустую библиотеку. Удаление подтверждается только успешной полной сверкой.

## Экраны MVP

1. **Регистрация и вход.** Email/password, активные сессии и выход со всех устройств.
2. **Подключения.** Список источников, состояние сессии, последняя успешная синхронизация, «Синхронизировать сейчас», переподключение и удаление.
3. **Личная библиотека.** Единый список произведений, статус и прогресс отдельно по каждому источнику.
4. **Произведение.** Исходные названия, ссылки на площадки, прочитанная глава на каждой площадке и время наблюдения.
5. **Проверка совпадений.** Подтвердить, разделить или отложить неоднозначные пары тайтлов.
6. **Журнал синхронизации.** Понятный итог запуска без cookies, токенов, тел ответов и технических секретов.

## API MVP

Better Auth обслуживает `/api/auth/*`. Продуктовый API версионируется отдельно:

```text
GET    /api/v1/me

GET    /api/v1/sources
GET    /api/v1/connections
POST   /api/v1/connections
GET    /api/v1/connections/:id
DELETE /api/v1/connections/:id
POST   /api/v1/connections/:id/auth-sessions
GET    /api/v1/auth-sessions/:id
POST   /api/v1/connections/:id/reauth
POST   /api/v1/connections/:id/sync

GET    /api/v1/library
GET    /api/v1/library/:workId
GET    /api/v1/library/:workId/sources

GET    /api/v1/match-candidates
POST   /api/v1/match-candidates/:id/resolve

GET    /api/v1/sync-runs
GET    /api/v1/sync-runs/:id
GET    /api/v1/events
```

`GET /api/v1/events` использует SSE для прогресса первичного импорта; отдельная WebSocket-инфраструктура для обычного интерфейса не нужна.

## Критерии готовности MVP

- Пользователь создаёт профиль и подключает ReManga и MangaLib.
- В Manga Hub попадают все доступные записи из его личных библиотек и никакой глобальный каталог.
- Для каждой записи видны исходный статус, подтверждённый прогресс и время последней проверки.
- Одинаковые произведения с двух источников объединяются уверенно либо отправляются на ручную проверку.
- Изменение, сделанное на Android, появляется после фоновой синхронизации без ручного перезапуска.
- Истёкшая сессия запрашивает повторный вход и не уничтожает накопленные данные.
- Cookies/tokens отсутствуют в открытом виде в БД, логах, job payload и резервных копиях.
- Повторный запуск, сетевой сбой и перезапуск процессов не создают дубликатов и не откатывают прогресс.
- Локальный и Docker-запуск используют одну схему БД, одни миграции и одни команды приложения.

## Не входит в этот MVP

- полный публичный каталог и поисковик по всем тайтлам площадок;
- размещение страниц манги, собственная читалка и нейроперевод;
- рекомендации;
- импорт браузерной истории;
- добавление произведений или запись прогресса обратно на внешние сайты;
- нативное Android-приложение;
- платные подписки, социальные функции и публичные профили.

## Следующая итерация: обратная синхронизация

После стабильного read-only MVP можно добавить запись прогресса обратно на источники. Она включается пользователем отдельно для каждого подключения и работает только для произведений, уже находящихся в обеих внешних библиотеках. Перед записью нужны точное сопоставление глав, preview изменений, повторное чтение текущего состояния и проверка результата. Неоднозначные главы и тайтлы никогда не отправляются автоматически.

## Ближайшая задача

Провести первый ручной end-to-end прогон на тестовых аккаунтах ReManga и MangaLib: войти через worker, подтвердить полноту импорта личной библиотеки, сравнить прогресс с Android и проверить повторную синхронизацию через час. После этого добавить ручной повтор sync/reauth в UI и remote browser gateway для серверного запуска.
